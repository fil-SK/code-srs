## 1. Executive assessment

### **READY AFTER P1 FIXES**

| Severity | Count |
|---|---|
| **P0** | **0** |
| **P1** | **4** (one applies only if you deploy with Supabase configured) |
| **P2** | **10** |
| **P3** | **12** |

The codebase is in genuinely good shape. Security posture is strong and mostly *structurally* strong rather than
accidentally strong: there is no `dangerouslySetInnerHTML`, no `eval`, no `innerHTML`, no attacker-reachable URL
construction, no committed secret, exactly two `VITE_` variables (both browser-safe by design), one auth storage
seam that nothing else touches, one repository seam that no component bypasses, and RLS policies that correctly
scope every Supabase table to `auth.uid()` on both `using` and `with check`. The quality gates are clean and the
end-to-end review loop works keyboard-only in a real browser with no console errors.

The four P1s are not architectural. Two are single-function defects with proven reproductions, one is a one-line
coherence gap in `AuthProvider`, and one is a missing pagination loop in the Supabase backend. None requires a
redesign.

The two that matter most:

1. **Replace-mode import can destroy a user's workspace and then fail.** Proven in Chromium: a backup file that
   passes `parseBackup` wipes all five stores and *then* throws a raw IndexedDB `DataError`. The prior workspace is
   gone and the user is shown a failure message. This directly contradicts the guarantee written in
   `src/data/backup.ts:28`.
2. **Every local-calendar-day calculation breaks across a DST transition.** Proven in Node: ten consecutive days of
   reviews spanning 2026-10-25 report a current streak of **4** and a best of **6**. The next European DST
   transition is roughly two months out, so on a public MVP this is a scheduled, not hypothetical, regression of the
   product's headline engagement metric.

## 2. Release blockers (P0 / P1)

### P1-1 · Replace-mode import clears the workspace before a write that can still fail

**Severity:** P1 **Area:** Data safety / backup-restore guarantee **Confidence:** High (reproduced)

**Evidence**

- [src/data/backup.ts:29-54](src/data/backup.ts#L29-L54) — `importBackup` runs `Promise.all([...5 clear()s])` and then
  `Promise.all([...5 bulkPut()s])`. Neither group is a transaction, and there is no rollback.
- [src/domain/io/backup.ts:83-97](src/domain/io/backup.ts#L83-L97) — `parseBackup` validates `cards`, `decks` and
  `reviewLogs` element-by-element, but `drafts` and `roadmaps` receive **`Array.isArray` and nothing else**. The
  comment at line 92 states this deliberately ("Drafts and roadmaps keep list-presence validation only").
- [src/data/backup.ts:26-28](src/data/backup.ts#L26-L28) — the code comment claims the opposite of the observed
  behaviour: *"runs BEFORE the replace-mode `clear()` so a rejected import can never leave the store half-written."*

**Reproduction (executed against `npm run preview` in headless Chromium)**

1. Sign in with the demo workspace; import a valid backup containing deck `PRIOR USER DECK`. → present in `/decks`.
2. Select **Replace**, import a file that is structurally valid except `"roadmaps": [{ "title": "no id here" }]`.
3. Confirm the "Replace all current data?" dialog.

Observed:

```
BEFORE  -> PRIOR USER DECK present: true
ERROR SHOWN -> Failed to execute 'put' on 'IDBObjectStore':
               Evaluating the object store's key path did not yield a value.
AFTER   -> PRIOR USER DECK present: false      <-- prior workspace destroyed
AFTER   -> INCOMING DECK present  : true
```

**Expected** — a file the app refuses must leave storage untouched, per the module's own contract.

**Actual** — validation passes, `clear()` wipes cards/decks/drafts/reviewLogs/roadmaps, `bulkPut` on the malformed
roadmap rejects because IndexedDB cannot derive the inline `id` key, and the user sees a raw browser error string
next to an emptied library.

**Impact** — total, unrecoverable loss of everything the incoming file did not itself contain. The malformed-element
path is the cheapest trigger, but it is not the only one: because the clear and the write are separate transactions,
**any** mid-write failure has the same effect — IndexedDB quota exhaustion on a large replace import, or a Supabase
network/RLS error in cloud mode. The documented AI-generation prompt
([docs/prompts/ai-card-prompt.md](docs/prompts/ai-card-prompt.md#L46-L55)) does instruct empty `drafts`/`reviewLogs`,
so a well-behaved generator is safe; a hand-edited file, an older export, or a generator that improvises is not.

**Recommended fix direction** — smallest first: extend `validateBackupEntities` with `assertValidDrafts` /
`assertValidRoadmaps` (id + basic shape) so nothing unvalidated reaches `bulkPut`. Then make replace atomic — a
single Dexie `db.transaction('rw', ...)` spanning clear + write, or (backend-agnostic) snapshot via `exportBackup()`
before the clear and restore on failure. Also replace the raw `DataError` surface with a message that states whether
data was written.

### P1-2 · Fixed 86,400,000 ms day arithmetic breaks every local-day statistic across DST

**Severity:** P1 **Area:** Reliability / correctness **Confidence:** High (reproduced)

**Evidence**

`startOfDay` ([src/domain/stats/dateRange.ts:10-14](src/domain/stats/dateRange.ts#L10-L14)) correctly produces a
**local** midnight. Every consumer then steps between days with the **fixed** `DAY_MS` constant, which is wrong by an
hour on the two days a year a local day is 23 h or 25 h long:

| Consumer | Line | Broken expression |
|---|---|---|
| `computeStreak` | [streak.ts:32-45](src/domain/stats/streak.ts#L32-L45) | `cursor -= DAY_MS`, `d - prevDay === DAY_MS` |
| `computePaceSeries` | [todayMetrics.ts:124-143](src/domain/stats/todayMetrics.ts#L124-L143) | `today - 6*DAY_MS`, `d += DAY_MS` |
| `computeHeatmap` | [progressMetrics.ts:173-189](src/domain/stats/progressMetrics.ts#L173-L189) | `today - (days-1)*DAY`, `d += DAY` |
| `deriveMilestones` | [progressMetrics.ts:335](src/domain/stats/progressMetrics.ts#L335) | `d - prevDay === DAY` |
| `formatEventDate` | [dateRange.ts:73](src/domain/stats/dateRange.ts#L73) | `today - day === DAY` ("Yesterday") |
| `buildRange` / `previousPeriod` | [dateRange.ts:33-44](src/domain/stats/dateRange.ts#L33-L44) | `to - days * DAY` |

**Reproduction** (Node, machine timezone Europe/Belgrade — same CET/CEST rules as Stockholm; reviews placed at local
noon on ten consecutive days, Oct 20–29 2026, DST ends Oct 25):

```
computeStreak -> { current: 4, best: 6 }        (expected { current: 10, best: 10 })

paceSeries ->
  Fri Oct 23 2026 01:00:00   count 0      <-- reviews exist, bucket key drifted to 01:00
  Sat Oct 24 2026 01:00:00   count 0
  Sun Oct 25 2026 01:00:00   count 0
  Mon Oct 26 2026 00:00:00   count 1
  ...
```

**Expected** — a learner who studied every day has an unbroken streak, and each of the seven pace buckets counts the
reviews that happened on that local day.

**Actual** — after any DST transition the streak silently truncates to the days since the transition (and the *best*
streak is permanently capped at the longest DST-free run in history, since it is recomputed from the same logic).
The 7-day pace chart shows zeros for days that have reviews. The activity heat map mis-buckets the same way, and
`deriveMilestones` will never award a streak badge for a run that crosses a transition.

**Impact** — every user in a DST-observing timezone, twice a year, deterministically. Streak is the product's most
visible engagement number and is rendered in the top nav on every page. The next European transition is
**2026-10-25**. Note this is *presentation* corruption only — `ReviewLog.reviewedAt` and `Card.scheduling.due` are
absolute epoch millis and are unaffected, so nothing is persisted wrongly and a fix is retroactive.

**Recommended fix direction** — add `addDays(ms, n)` / `dayDiff(a, b)` helpers next to `startOfDay` that go through
`Date.setDate()` (calendar arithmetic) rather than millisecond addition, and route all six consumers through them.
`startOfDay` itself needs no change. Add a test that pins a DST date via the fixture, not via the machine clock.

### P1-3 · A local/demo session counts as authenticated while the Supabase backend is active

**Severity:** P1 **Area:** Auth coherence **Confidence:** High (code-verified) · reachable only on a config transition

**Evidence**

- [src/auth/AuthProvider.tsx:104](src/auth/AuthProvider.tsx#L104) — `isAuthenticated: session !== null || local !== null`.
  The predicate never consults `isSupabaseConfigured`.
- [src/data/index.ts:11-18](src/data/index.ts#L11-L18) — the repository is chosen purely from
  `isSupabaseConfigured`; it does not consult the session at all.
- [src/components/layout/AccountMenuContent.tsx:146-151](src/components/layout/AccountMenuContent.tsx#L146-L151) — a
  `local`-kind identity renders the data-location line as **"Stored in this browser."**

**Failure scenario** — an origin that previously ran local-first (users hold `itera.session` in `localStorage`) later
gets `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` at build time. This is the project's own stated path:
[docs/CURRENT_STATE.md §22](docs/CURRENT_STATE.md#L303-L305) lists migrations 0002/0003 as still needing to be run
against a Supabase project. On the next visit:

- `RequireAuth` admits the user (`local !== null`), so `/login` is never shown — and `LoginPage` actively redirects
  away from itself because `isAuthenticated` is true.
- `getRepository()` returns `SupabaseRepository`, whose requests carry the **anon** JWT.
- The `own rows` policies are `for all to authenticated`, so anon matches no policy: every `select` returns an empty
  `200` and every write fails. The user sees an empty, silently broken workspace.
- The account menu tells them their data is "stored in this browser". It is not — the app is reading Supabase.

**Expected** — with Supabase configured, only a Supabase session is a session; a stale local session must not admit
someone to a cloud-backed app.

**Impact** — no data exposure (RLS holds correctly; this is *not* an authorization bypass). But the app is
unusable, gives no diagnosis, offers no route back to `/login` except discovering **Sign out**, and displays a false
statement about where the user's data lives. Deliberate local/demo password behaviour is explicitly out of scope for
this finding — the problem is the *mode mismatch*, not the demo shell.

**Recommended fix direction** — make the predicate mode-aware in one place, e.g.
`isAuthenticated: isSupabaseConfigured ? session !== null : local !== null`, and clear any local session on first
boot when Supabase is configured. Everything else in the auth path already flows from `isAuthenticated`.

### P1-4 · `SupabaseRepository` never paginates, so reads silently truncate at the project row cap

**Severity:** P1 (Supabase mode only) **Area:** Supabase / backup integrity **Confidence:** Medium — cannot be verified against a live project

**Evidence**

Every read in [src/data/supabase/SupabaseRepository.ts](src/data/supabase/SupabaseRepository.ts) issues one
unbounded `select` with no `.range()` and no follow-up page: `crud.getAll` (line 30), `cards.getDue` (line 76),
`cards.search` (line 101), `reviews.all` (line 139), `reviews.forCard` (line 148), `reviews.range` (line 157).

Supabase projects carry an API-level **Max rows** setting (Project Settings → API), whose platform default is
**1000**. PostgREST enforces it by returning the first N rows — silently, with a `200`.

**Failure scenario** — a cloud-mode user with more than the cap in any table:

- `exportBackup` ([src/data/backup.ts:9-19](src/data/backup.ts#L9-L19)) calls `repo.*.getAll()` / `repo.reviews.all()`
  directly. **The exported "backup" is silently incomplete** — this is the single worst consequence, because the
  file looks normal and the loss is only discovered on restore.
- Progress KPIs, retention, streak and the heat map all read `useReviewLogs()` → `reviews.all()`. Review logs are
  the fastest-growing table; 1000 is reachable within weeks of daily study.
- `search` powers the whole Library; `getDue` powers `/review` and Today's hero.

**Expected** — the storage seam returns the complete result set on both backends. Parity is an explicit invariant
([docs/CURRENT_STATE.md §12](docs/CURRENT_STATE.md#L174-L182): "all text/tag/type filtering happens in memory
identically in both backends so results match").

**Actual** — Dexie returns everything; Supabase returns at most the project cap, with no error and no signal.

**Impact** — a corrupted backup file presented as a successful export, plus wrong analytics and a short review queue.
Not applicable at all if you ship local-only.

**Recommended fix direction** — a small `selectAll(query)` helper that loops `.range(offset, offset + PAGE - 1)`
until a short page comes back, used by all six read sites. Independently, confirm the project's Max rows value.

### Configuration / deployment risks (not vulnerabilities)

- **`supabase/schema.sql` is not re-runnable.** Tables use `create table if not exists`, but the four `create policy
  "own rows"` statements for `cards`/`decks`/`drafts`/`review_logs` have no `drop policy if exists` guard — only the
  later `roadmaps` block does ([schema.sql:107](supabase/schema.sql#L107)). Re-running the script against an existing
  database aborts at the first policy. Not destructive (the SQL editor rolls back), but it makes "just re-run the
  schema" a misleading instruction. **P2.**
- **Migrations 0002 and 0003 remain live-unverified**, exactly as the docs state. See §4.

### Theoretical, not currently exploitable

- Every table uses a **global** `id text primary key` rather than `(user_id, id)`. Two users cannot hold the same
  row id; a deliberate insert of a colliding id would surface as a constraint error (Postgres evaluates the UPDATE
  policy on `on conflict`, so no cross-user write occurs). With 128-bit v4 UUIDs from
  [newId()](src/lib/id.ts#L16-L30) this is an existence oracle at best, and one that requires already knowing a
  victim's UUID. **P3 — leave alone.**

## 4. Data-safety findings

### Backup / import

- **P1-1 above** is the significant one.
- **Validation quality is otherwise high.**
  [validateBackupEntities.ts](src/domain/io/validateBackupEntities.ts) checks card `schemaVersion` against the app's
  own `CARD_SCHEMA_VERSION` (not merely "is a number"), rejects `NaN`/`Infinity` explicitly
  ([line 62](src/domain/io/validateBackupEntities.ts#L62)), validates every scheduling field through a
  `Record<keyof Required<SchedulingState>, …>` table so a new field fails the build, and validates all six
  interaction payload shapes through a `Record<InteractionType, …>` that a seventh type would break. Version
  handling is correct in both directions: `> BACKUP_VERSION` and `< MIN_SUPPORTED_BACKUP_VERSION` both throw with
  distinct, honest messages.
- **The prototype-history contract holds.** `assertValidReviewLogs` requires `stateBefore` ∈ the four state kinds
  ([line 270-279](src/domain/io/validateBackupEntities.ts#L270-L279)), so a nonconforming ReviewLog cannot re-enter
  through import. This matches the Dexie v2 upgrade and migration 0003. Verified.
- **Referential integrity is mode-correct.** `assertDeckReferencesResolve`
  ([src/data/backup.ts:56-75](src/data/backup.ts#L56-L75)) unions the file's decks with the repository's decks under
  Merge and only the file's under Replace, and runs *before* `clear()`. The rule itself is right; P1-1 is that it is
  not the only thing that can fail after that point.
- **Resource exhaustion:** not a realistic concern. Import is a local file the user chose; there is no remote input
  surface. `parseBackup` does a single `JSON.parse` and rejects malformed JSON with a friendly message.
- **Cyclic `Deck.parentId` in an imported file hangs the tab.** `collectionPathFor`
  ([collectionTree.ts:96-109](src/features/library/collectionTree.ts#L96-L109)) walks `parentId` with an unguarded
  `while (current)` and `path.unshift`. Deck `parentId` is deliberately not validated referentially, and cycles are
  not checked. `buildDeckTree`, `subtreeIds` and `buildCollectionTree` are all cycle-safe by construction — this one
  function is not. **Not reachable through the UI**: `DeckSettings` excludes the deck's own subtree from the parent
  list ([DeckSettings.tsx:30-33](src/features/library/DeckSettings.tsx#L30-L33)). Import is the only path. **P2.**

### Deletion — verified safe

Deck deletion is **guarded on both surfaces** and cannot orphan cards:

- [LibraryBrowserPage.tsx:124-138](src/features/library/LibraryBrowserPage.tsx#L124-L138) — refuses a deck with any
  cards (count includes suspended, since it comes from `useSearchCards({ includeSuspended: true })`).
- [LibraryCollectionView.tsx:153-172](src/features/library/LibraryCollectionView.tsx#L153-L172) — refuses a
  Collection with child decks *or* direct cards.

Consequently `useDeleteDeck`'s bare `repo.decks.delete(id)` never leaves a dangling `card.deckId`. A child deck can
still be left with a dangling `parentId` in edge orderings; that is the **documented tolerance**
(`buildDeckTree` treats it as a root) and is **not** a defect. ReviewLogs for a deleted card are intentionally
retained and rendered as `(deleted card)` — also documented, also correct.

### Migrations

`supabase/schema.sql` and the three migration files are **consistent with each other and with the code**:

- 0002 drops `card_states` before `cards` (the FK cascades) — the ordering comment is correct.
- 0003's check constraint text is byte-identical to the one in `schema.sql`, and both match
  `SCHEDULING_STATE_KINDS` in the validator and `SchedulingStateKind` in the types. No drift.
- 0003 re-asserts the grant after the constraint change, per the project's own convention.
- `card_states` is correctly absent from `schema.sql`, matching the single-card-model convergence.

**Classification of the unverified-migration risk, as requested:**

| | 0002 | 0003 |
|---|---|---|
| Code-review concern | none found | none found |
| Actual proven defect | none | none |
| Unverified deployment risk | **yes** — destructive by design (drops `cards`), no rollback | **yes** — destructive by design (`delete from review_logs`), rollback drops the constraint only |

Both are written to the same standard as the rest of the schema and read as correct. The risk is that neither has
ever been executed. Run them against a scratch Supabase project before a real one.

### Dexie

- Schema matches current entities exactly ([db.ts:24-30](src/data/dexie/db.ts#L24-L30)): `cards: 'id, deckId, *tags,
  scheduling.due'`, `decks: 'id, parentId, name'`, `drafts`, `reviewLogs: 'id, cardId, reviewedAt'`, `roadmaps`.
  Booleans are correctly not indexed.
- **The v2 upgrade does exactly what the docs claim.** `this.version(2).upgrade((tx) => tx.table('reviewLogs').clear())`
  with no `.stores()` call carries the v1 schema forward and clears only `reviewLogs`. It runs only on an actual
  1→2 upgrade; a fresh database created at v2 skips it. Correct.
- **The old-database deletion cannot touch the live database.** [db.ts:40](src/data/dexie/db.ts#L40) is
  `Dexie.delete('code-srs')`, a hard-coded literal. The active database is `'itera'` (the constructor default), and
  the only other names passed to `AppDB` are per-test ones. There is **no** path — no variable, no template string,
  no env value — by which this could target the current database. Verified safe.
- Due queries are correct: the `scheduling.due` index narrows, then `!c.suspended` filters in memory, so **suspended
  cards cannot leak into due results** on this backend.

## 5. Reliability / correctness findings

Beyond P1-2 (DST), all P2/P3:

- **Review persistence is two non-atomic writes.**
  [useReview.ts:61-66](src/hooks/useReview.ts#L61-L66) does `await repo.cards.put(graded)` then
  `await repo.reviews.append(log)`. If the log write fails, the card's scheduling has already advanced with no
  history row — permanently invisible in Progress and unreconstructible. Low probability on Dexie, higher on
  Supabase. **P2.**
- **A failed persist leaves the session stuck with no error UI.**
  [ReviewSessionScreen.tsx:159](src/features/reviewV2/ReviewSessionScreen.tsx#L159) calls `onGraded?.(result)`
  fire-and-forget; `ReviewSessionV2.handleGraded` is `async` and awaits the mutation
  ([ReviewSessionV2.tsx:35-39](src/features/review/ReviewSessionV2.tsx#L35-L39)). A rejection becomes an unhandled
  promise rejection: the phase has already dispatched `GRADED`, ratings are disabled, and `setIndex` never runs. The
  card is stuck and nothing tells the user why. **P2.**
- **What is *correct* in the review path** (verified in a real browser, keyboard-only, `Space` → `3` → `Space` → `3`
  → "All done"):
  - one grade → exactly one state transition and exactly one ReviewLog (confirmed in `/progress/history`: 2 reviews
    for 2 cards);
  - `stateBefore` is genuinely pre-grade — `schedulingBefore={current.scheduling}` reads the snapshot's card, and
    `buildReviewLog` takes `before` from that same object, never from the FSRS log;
  - persistence does **not** recompute — `usePersistReviewResult` writes the `{after, log}` `reviewService.submit`
    already produced, so session and store cannot diverge;
  - double-grade is guarded: `rate()` returns early unless `phase.kind === 'feedback'` and dispatches
    `CHOOSE_RATING` synchronously before awaiting; the key handler ignores `e.repeat`;
  - objective grading is separate from the FSRS rating — `autoGrade` produces an `ObjectiveResult` that only
    *suggests* a rating, and a genuine `null` is deliberately preserved rather than coerced to "incorrect"
    ([ReviewSessionScreen.tsx:137-143](src/features/reviewV2/ReviewSessionScreen.tsx#L137-L143));
  - the queue snapshot cannot be reshaped by invalidation — `useSessionQueue` only re-snapshots on a `scopeKey`
    change, and `ReviewSessionV2` is keyed on `session.id`;
  - undo restores the pre-grade card verbatim and deletes the log by id; the completion screen's undo is `busy`-guarded.
  - `ts-fsrs` itself was treated as a trusted dependency; only Itera's integration was audited.
- **`AuthProvider` has no `.catch` on the session bootstrap.**
  [AuthProvider.tsx:56-59](src/auth/AuthProvider.tsx#L56-L59) — if `getSession()` rejects, `setLoading(false)` never
  runs and `AuthGate` shows "Loading…" **forever**. This is the one path that can produce a permanently blank app.
  **P2.**
- **`downloadText` revokes the object URL synchronously and never attaches the anchor.**
  [download.ts:9-13](src/lib/download.ts#L9-L13). Works in Chromium; this is the pattern that has historically
  failed in Firefox/Safari. Since Export is the app's *only* backup path, a silent no-op there is worse than it
  looks. **P2.**

## 8. Backend parity

### **Dexie / Supabase parity: ISSUES FOUND**

Concrete divergences:

1. **Row-cap truncation (P1-4).** Dexie returns the full result; Supabase returns at most the project's Max rows for
   every read. This is the material one.
2. **Suspended-card semantics differ in `getDue`.**
   Dexie filters `!c.suspended` in memory ([DexieRepository.ts:47](src/data/dexie/DexieRepository.ts#L47)), which
   treats a missing `suspended` as not-suspended. Supabase filters `.eq('suspended', false)`
   ([SupabaseRepository.ts:79](src/data/supabase/SupabaseRepository.ts#L79)) against a generated column that is
   **`NULL`** when the key is absent — and `eq false` excludes `NULL`. A card without `suspended` would be due on
   Dexie and permanently invisible on Supabase. **Currently unreachable**: `createCard` always writes
   `suspended: false`, every `save*Card` edit path preserves it, and the backup validator *requires* a boolean. So
   this is a latent trap, **P3**, worth a comment rather than a fix. Note the same field is filtered *in memory* in
   Supabase's `search` (line 105), so the two Supabase queries already disagree with each other about `NULL`.

Everything else matches, by design and by construction:

- `search` and `getDue` share one `searchableText` implementation and identical in-memory predicate order and sort
  (`updatedAt` desc / `scheduling.due` asc) in both files.
- Deck filtering is `c.deckId === deckId` on both; **subtree** scoping happens above the seam in
  [ReviewPage.tsx:31-36](src/features/review/ReviewPage.tsx#L31-L36) via `subtreeIds`, so it cannot diverge.
- Tag filtering, type filtering, `limit` slicing: identical code.
- `reviews.range` is inclusive on both (`between(from, to, true, true)` vs `.gte/.lte`); `forCard` sorts ascending
  on both; `append` rejects a duplicate id on both (Dexie `add`, PostgREST `insert`).
- `bulkPut` upserts on both; `clear()` is RLS-scoped on Supabase via `.neq('id','')`.

**Not fully verifiable:** everything about Supabase was verified statically only. There is no live project (the
owner's was deleted mid-development), and `src/data/supabase/` has **zero tests** (§9).

### The intermittent flake

I did not attempt to trigger it by re-running the suite. Two structural sources exist; I can name both with
evidence, and I will not claim either is *the* cause.

**Hypothesis A — a run crossing local midnight (best fit for the reported signature).**
`StreakBadge.test.tsx` and `TodayPage.test.tsx` build fixtures from the **real** clock and then assert against a
component that reads the real clock again, milliseconds to seconds later:

```js
// src/components/layout/StreakBadge.test.tsx:18-20
const d = new Date(); d.setDate(d.getDate() - daysAgo); d.setHours(10, 0, 0, 0)
```

If the seed is built at 23:59:59.9 and `computeStreak(Date.now())` runs at 00:00:00.1, `log(0)` lands on
*yesterday* and every count shifts by one. That fails **exactly one test in exactly one run**, at most once per day
— which matches "one failure among nine runs on 2026-08-22" far better than a load-related timeout would.

**Hypothesis B — RTL's 1000 ms default `findBy*` timeout under CPU contention.**
No `asyncUtilTimeout` is configured anywhere (`vitest.config.ts` and `src/test/setup.ts` set none). About twenty
component test files `await screen.findBy…` on a TanStack Query → Dexie/fake-indexeddb round trip. The suite's own
recorded wall-clock varies **36.0 s → 54.7 s → 46.5 s** on the same machine, i.e. ±50 % scheduling variance, which
is enough to push a 1 s wait over on a busy run.

**Also worth knowing:** `StreakBadge.test.tsx:104` — `expect(log(1).reviewedAt - log(2).reviewedAt).toBe(DAY)` — is
a *deterministic* failure on the day after every DST transition, for the same reason as P1-2. It is not the observed
flake (it would fail every run that day, not one of nine), but it is a dated time bomb in the suite.

**Preserved as an unresolved P2 observation.** On recurrence: capture the **complete** output, not the tail —
`npx vitest run > run.log 2>&1` — plus the wall-clock time the run started and finished, and `Intl.DateTimeFormat().resolvedOptions().timeZone`.
If the failing test is in `StreakBadge`/`TodayPage` and the run straddled midnight, Hypothesis A is confirmed.

## 14. Recommended remediation order

There are **no P0 findings**. There are **four P1s**, all narrow.

1. **P1-1 — Replace-import data loss.** Validate `drafts`/`roadmaps` elements *and* make the replace path atomic.
   Highest impact, and the only finding that can destroy data a user cannot get back.
2. **P1-2 — DST day arithmetic.** Add calendar-aware `addDays`/`dayDiff` and route the six consumers through them.
   Time-boxed by the 2026-10-25 transition — if you ship before then it is not a launch-day defect, but it becomes
   one on a fixed date.
3. **P1-3 — Mode-aware `isAuthenticated`.** One line. Do it before you ever set `VITE_SUPABASE_*` on a public origin.
4. **P1-4 — Supabase pagination.** *Only if you deploy with Supabase configured.* If the MVP ships local-only, defer
   it — but then also do not enable Supabase later without doing 3 and 4 together.
5. **Selected P2s, in this order:** §10 items 3, 4, 8, 9, 11 (five tiny, risk-free changes), then 5, 6, 7.
6. **Re-run the full gate set** (`vitest`, `tsc -b --force`, `lint`, `build`) and re-verify the replace-import
   reproduction from §2 no longer loses data.
7. **Before enabling Supabase at all:** run `schema.sql`, then `0002`, then `0003` against a scratch project and
   confirm CRUD works for two separate users; check the project's **Max rows** setting.
8. **Release.**

Items 10 and 12 from §10 (Supabase tests, import error copy) are worth doing in the first post-MVP pass. Everything
in §11 should be left alone.
