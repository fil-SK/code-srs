Record of material implementation/design assumptions made during the redesign, so later phases stay consistent. Append to this file; do not rewrite history — if a decision is later reversed, add a new entry noting the reversal rather than editing the old one.

**D1. Treating the pasted spec as the authoritative design direction, sourced from this project's own earlier ChatGPT-brief workflow.**
The spec (`itera_claude_master_spec.md`) and logo arrived together with implementation instructions in one message. Cross-checked: the spec's Today mockup greets "Fica," matching the project owner's name from prior context, and its content is a direct, much-expanded answer to a condensed redesign brief written earlier in this project for pasting into ChatGPT. Treated as genuine, not as an untrusted external document.

**D2. FSRS wrapper (`src/domain/scheduling/scheduler.ts`) reviewed with no defects found; not rewriting it.** *(Reframed in the correction pass — see D-correction-pass and `itera-migration-plan.md` §9: this was a manual code-review conclusion, not a test-verified one, and should not have been stated as flatly "verified.")*
The spec's default posture is suspicion of AI-generated FSRS code (§9.5: "must not be trusted without verification"). Audited the `CardInput`/`Card` ↔ `SchedulingState` mapping field-by-field against `ts-fsrs`'s types; found it complete and consistent by inspection. Decision: retain the module as-is (do not rewrite), add a `ReviewService` boundary around it in Phase E for the spec's architectural separation (not because the logic is wrong), and add golden/invariant tests before Phase D's CardState cutover relies on it as a fully verified boundary.

**D3. Deferred the Roadmaps conflict rather than resolving it unilaterally.**
`src/features/roadmaps/**` is a fully shipped, live-in-production feature (built the same day this spec arrived) whose entity type (nodes referencing Decks, directed edges) is not mentioned anywhere in the spec, and which spec §36 explicitly lists under Deferred Scope: "Do not implement... unless explicitly requested." Deleting a shipped feature is a destructive, user-visible action the spec's own escalation rules (§2.3) reserve for the product owner. **No code was deleted.** Flagged as Q1 in the audit summary.

**D4. Deferred the rebrand's infrastructure scope rather than assuming full rename.**
The spec locks the name "Itera" and a new logo (§4.1–§4.2) as product identity, but says nothing about the GitHub repo name, the Vercel project/domain (`code-srs.vercel.app`), or whether the existing `CLAUDE.md`/`.claude/` docs should be renamed. Treated the product-facing name/brand as locked per spec, but treated "which real-world artifacts get renamed and when" as outside what's answerable from the repo or spec alone. Flagged as Q2.

**D5. Preview routes will be additive under a `/design-preview/*` prefix rather than replacing any existing route.**
Chosen so Phase B/C work can proceed and be reviewed without any risk to `/`, `/decks`, `/review`, etc. Matches spec §34 Phase B's explicit route list and §2.2's "do not replace existing screens before the audit is reviewed."

**D6. Card v2 types will live alongside the current `Card` union during Phases C–D, not replace it in place.**
Chosen so the exhaustive-switch compile-time safety this codebase already relies on (registry, `searchableText`, `cardTypeMeta`, `seedContent`) continues to catch incomplete migration work, rather than a big-bang type swap that compiles by accident with missing cases.

**D7. `ReviewLog`/`ReviewEvent` will be *extended*, not restructured to the letter of spec §9.3.**
Spec explicitly permits adapting field names/shapes to the project (§9.3 preamble: "Adapt names to the project"). The current `ReviewLog` (immutable, one row per review, exact before/after deltas) is sound; will add `sessionId` and `interactionType` where the new Review flow makes them available, rather than redesigning the log format wholesale.

**D8. Collection/Deck split will be derived from existing `parentId` structure, not authored fresh by users.**
Any existing Deck with children becomes a Collection; any Deck with no children (leaf) becomes a Deck, placed at the root of "Unfiled" if it has no ancestor chain worth preserving as a Collection. *(Phase reference corrected: this is `itera-migration-plan.md` §6 / `itera-redesign-plan.md` Phase G, not "Phase F" as originally written here — Phase F is Create/Edit. See D14/D15 for how the ambiguous case and migration rigor were further corrected.)*

## 2026-07-22 — Correction pass

The product owner reviewed the four documents and issued eleven specific corrections. Applied throughout `itera-repository-audit.md`, `itera-redesign-plan.md`, this file, and `itera-migration-plan.md`. Recorded here rather than silently edited into the originals, per this doc's own policy.

**D11 (supersedes D9). Roadmaps: excluded from MVP navigation, data preserved, no destructive action without separate explicit approval.**
The product owner's earlier answer ("Drop it for now," picked from a scoped multiple-choice question) is a **provisional working assumption**, not a confirmed decision — it was not explicitly stated in freeform conversation, and D9's write-up over-specified it into destructive deletion, which the product owner then corrected. The actual default going forward: Roadmaps is excluded from the redesigned MVP navigation and gets no new development; existing Roadmap data (the `Roadmap` type, both backends' repo methods, the Supabase `roadmaps` table, and its presence in backup export/import) is **preserved, untouched**; the old Roadmap UI route may be hidden or retired **only once** its Deck references would become incompatible with the Collection/Deck split (`itera-redesign-plan.md` Phase G/H) — not before, and not as a blanket "delete in cleanup" as D9 said. Destructive deletion of Roadmap data is a separate decision requiring explicit approval, and is not scheduled by this plan.

**D12 (supersedes D10). Rebrand scope: in-app only, still a provisional working assumption.**
Same correction as D11 regarding confirmation status: this is what the product owner selected when asked, but is recorded as a **provisional assumption**, not a confirmed decision, until stated explicitly in this conversation. The substance is unchanged from D10: "Itera" as name/logo/palette applies to the PWA manifest, in-app UI copy/chrome, and `README.md`; it does not (yet) apply to the GitHub repository name, the Vercel project/domain, or `package.json`'s internal `name` field. Revisit before committing to any public-facing rename.

**D13. Locked: Walkthrough supports multiple highlighted line ranges; Matching preserves its existing 3-part/fixed-column capability.**
Explicitly locked by the product owner in this conversation (not inferred from a scoped question — stated directly). The v2 data model (`WalkthroughStep.focus: Array<{startLine,endLine}>` and `MatchingInteraction.columns`/`relationships` in `src/types/cardV2.ts`) is intentionally more general than the spec's illustrative MVP examples (a single `{startLine,endLine}` range; a fixed two-column `sources`/`targets` shape). No existing content or capability is downgraded to match the simpler example schema. This resolves what `itera-migration-plan.md` previously listed as "needs product-owner confirmation only if you want the simpler spec shape instead" — the richer shape is now the confirmed target, not merely the default-absent-objection.

**D14. Migration strategy is split: lazy-on-read only for old Card payload adaptation; every other migration (CardState extraction, Collection/Deck split, any entity-reference or indexed-storage change) is explicit, dry-run-able, deterministic, idempotent, and reportable.**
Corrects the previous, broader framing in `itera-migration-plan.md` §3, which suggested the lazy-on-read philosophy proven for card-payload shape changes could extend by analogy to other migrations. It cannot: those other migrations change entity identity or cross-entity references, where an unreported, best-effort background migration is exactly the kind of risk the product owner flagged. See the shared migration-runner contract added to `itera-migration-plan.md` §0.

**D15. No "General" deck (or any other remedy for decks with both children and direct cards) is designed until the preflight report proves the case occurs.**
Corrects `itera-migration-plan.md` §6 (previous version), which proposed auto-creating a "General" deck as a recommended remedy before checking real data. The preflight report (`itera-redesign-plan.md` Phase G, step 1) is required to run and be reviewed first; only if it shows the case actually occurring is a remedy designed, chosen against real counts. The one fixed invariant regardless of remedy: zero Cards may be lost.

**D16. Supabase schema changes are versioned migration files checked into the repository (`supabase/migrations/NNNN_description.sql`), not solely ad hoc edits to `supabase/schema.sql` run by hand in the dashboard.**
Each migration file is self-contained: tables/columns, indexes, RLS, policies, grants, and rollback notes. `supabase/schema.sql` may still be updated afterward as a consolidated reference, but is no longer the primary record of what changed and when. Applies starting with Phase D's `card_states` table and Phase G's Collection/Deck schema changes; no migration files exist yet, since no schema changes have shipped.

## 2026-07-23 — Phase B/C first PR: implementation decisions and amendments

The product owner reviewed the pre-coding plan and issued five amendments before implementation proceeded. Applied during the build, not after — recorded here alongside the resulting design decisions.

**D20. `/design-preview/*` is a structurally separate top-level route, not a child of `AppShell`.**
`src/app/router.tsx` registers `design-preview` as a sibling of the `/` route object, with its own `children` array — not nested inside `AppShell`'s children. Chrome-free by construction: `AppShell`, `Sidebar`, and `BottomNav` are never imported or rendered on this path, not hidden via CSS after mounting.

**D21. Production's `FlipCard` (`src/components/ui/FlipCard.tsx`) was found to fail keyboard activation and accessible semantics, and was not modified — a new, separate primitive was built instead.**
The product owner asked for verification against eight criteria before reuse. Content-driven height, different-height faces, backface-visibility, reduced-motion, no clipping, and no fixed aspect ratio all held (inherited from the CSS mechanism). Keyboard activation and accessible semantics did not: the front face is a plain `<div onClick>` with no `tabIndex`, `role`, or key handler. Rather than edit the file production imports (touching `ReviewSession.tsx`'s dependency graph), a small, separate replacement was built: `src/features/reviewV2/components/FlipCard.tsx`, using its own namespaced CSS (`.itera-flip*` in `src/index.css`, a duplicate of the `.flip*` rules under distinct names) plus `role="button"`, `tabIndex`, `onKeyDown` for Enter/Space, `aria-pressed`, and `aria-hidden` on whichever face is currently the back. Zero footprint on any file production imports. Flagged as worth reconsidering in Phase E: either the production primitive gains the same accessibility fix (benefiting the live app too) or the two stay permanently separate — not decided here.

**D22. `CodeView`'s theme-context-driven syntax palette was a real defect under the app's default configuration, not an acceptable temporary gap — fixed at the root, not papered over with a CSS-only patch.**
The original plan excluded `--code-bg` from the `.itera-scope` token re-point specifically to avoid a light-chrome/dark-palette mismatch, treating the mismatch as an acceptable known gap. The product owner correctly rejected this: since the app defaults to dark mode for a user with no stored preference (`getInitialTheme()` in `src/app/theme.tsx`), the defect would be visible under the *default*, not an edge case. Root cause: `CodeView` chooses `oneDarkHighlightStyle` vs `defaultHighlightStyle` from live `ThemeContext`, not from a CSS variable, so no CSS override could fix it. Fix: `ThemeContext` is now exported from `src/app/theme.tsx` (one-line, purely additive — every existing consumer still goes through `useTheme()`/`ThemeProvider` unchanged), and `src/features/design-preview/ForceLightTheme.tsx` provides a static `{theme: 'light', ...}` value to its subtree, without touching `document.documentElement` or `localStorage`, leaving the app's real global theme completely unaffected outside that subtree. `--code-bg` is now included in `.itera-scope`'s re-point, since the palette and background now always agree.

**D23. One behavioral test suite was added for `RecallCardDemo`, requiring two new devDependencies not previously in this repo.**
`vitest.config.ts` runs `environment: 'node'` — no DOM — so component testing had no existing infrastructure. Added `@testing-library/react`, `@testing-library/user-event`, `@testing-library/dom` (a required peer), and `happy-dom` as devDependencies; the new test file opts into `happy-dom` via a per-file `// @vitest-environment happy-dom` pragma rather than changing the global config, so the rest of the suite (14 other files, unaffected) keeps its fast, DOM-free default. The test fixture deliberately contains no fenced code block: `RichText`'s code-block path mounts CodeMirror via `LazyCodeView`, which wants DOM APIs (`ResizeObserver`, layout measurement) `happy-dom` doesn't fully provide — a real environment-compatibility gap, not a shortcut. The real C++ code content is exercised by loading the live route, not by this automated test. Nine tests cover: Space reveals (checked via the revealed face's `aria-hidden` state, not text presence — both flip faces are always mounted, so text-presence queries can't distinguish reveal state), reveal happens synchronously regardless of motion settings, Tip disappears on reveal, Explanation/rating controls appear only after reveal, keys 1-4 select the expected rating and only after reveal, a rating shortcut does not fire again once submitted, Space targeted at a focused control is not double-handled (see the honest caveat below), Space is prevented from scrolling, and held-key repeat does not duplicate the reveal.
One test's real strength is limited and said so in its own comment, not silently: the "focused control" test exercises the `isInteractiveTarget` guard's code path, but in this component the guarded action (`if (!revealed) setRevealed(true)`) is idempotent either way, so the scenario can't currently fail without the guard — it's a regression pin for future non-idempotent actions, not proof the guard is currently load-bearing.

**D24. Testing-library/react's auto-cleanup does not engage in this repo's Vitest config (no `globals: true`), which caused every render in the new test file to accumulate in the same document until an explicit `afterEach(cleanup)` was added.**
Not a design decision so much as a debugging note worth keeping: two tests failed with element-count mismatches (multiple "Good" buttons found, nine copies of answer text found) before this was diagnosed and fixed locally within the one new test file (not added to the shared `src/test/setup.ts`, to avoid any risk to the 13 other, DOM-free test files).
