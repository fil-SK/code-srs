## 2026-07-23 — Phase B/C first PR: implementation decisions and amendments

The product owner reviewed the pre-coding plan and issued five amendments before implementation proceeded. Applied during the build, not after — recorded here alongside the resulting design decisions.

**D20. `/design-preview/*` is a structurally separate top-level route, not a child of `AppShell`.**
`src/app/router.tsx` registers `design-preview` as a sibling of the `/` route object, with its own `children` array — not nested inside `AppShell`'s children. Chrome-free by construction: `AppShell`, `Sidebar`, and `BottomNav` are never imported or rendered on this path, not hidden via CSS after mounting.

**D21. Production's `FlipCard` (`src/components/ui/FlipCard.tsx`) was found to fail keyboard activation and accessible semantics, and was not modified — a new, separate primitive was built instead.**
The product owner asked for verification against eight criteria before reuse. Content-driven height, different-height faces, backface-visibility, reduced-motion, no clipping, and no fixed aspect ratio all held (inherited from the CSS mechanism). Keyboard activation and accessible semantics did not: the front face is a plain `<div onClick>` with no `tabIndex`, `role`, or key handler. Rather than edit the file production imports (touching `ReviewSession.tsx`'s dependency graph), a small, separate replacement was built: `src/features/reviewV2/components/FlipCard.tsx`, using its own namespaced CSS (`.itera-flip*` in `src/index.css`, a duplicate of the `.flip*` rules under distinct names) plus `role="button"`, `tabIndex`, `onKeyDown` for Enter/Space, `aria-pressed`, and `aria-hidden` on whichever face is currently the back. Zero footprint on any file production imports. Flagged as worth reconsidering in Phase E: either the production primitive gains the same accessibility fix (benefiting the live app too) or the two stay permanently separate — not decided here.

**D22. `CodeView`'s theme-context-driven syntax palette was a real defect under the app's default configuration, not an acceptable temporary gap — fixed at the root, not papered over with a CSS-only patch.**
The original plan excluded `--code-bg` from the `.itera-scope` token re-point specifically to avoid a light-chrome/dark-palette mismatch, treating the mismatch as an acceptable known gap. The product owner correctly rejected this: since the app defaults to dark mode for a user with no stored preference (`getInitialTheme()` in `src/app/theme.tsx`), the defect would be visible under the *default*, not an edge case. Root cause: `CodeView` chooses `oneDarkHighlightStyle` vs `defaultHighlightStyle` from live `ThemeContext`, not from a CSS variable, so no CSS override could fix it. Fix: `ThemeContext` is now exported from `src/app/theme.tsx` (one-line, purely additive — every existing consumer still goes through `useTheme()`/`ThemeProvider` unchanged), and `src/features/design-preview/ForceLightTheme.tsx` provides a static `{theme: 'light', ...}` value to its subtree, without touching `document.documentElement` or `localStorage`, leaving the app's real global theme completely unaffected outside that subtree. `--code-bg` is now included in `.itera-scope`'s re-point, since the palette and background now always agree.

**D23. One behavioral test suite was added for `RecallCardDemo`, requiring two new devDependencies not previously in this repo.**
`vitest.config.ts` runs `environment: 'node'` — no DOM — so component testing had no existing infrastructure. Added `@testing-library/react`, `@testing-library/user-event`, `@testing-library/dom` (a required peer), and `happy-dom` as devDependencies; the new test file opts into `happy-dom` via a per-file `// @vitest-environment happy-dom` pragma rather than changing the global config, so the rest of the suite (14 other files, unaffected) keeps its fast, DOM-free default. The test fixture deliberately contains no fenced code block: `RichText`'s code-block path mounts CodeMirror via `LazyCodeView`, which wants DOM APIs (`ResizeObserver`, layout measurement) `happy-dom` doesn't fully provide — a real environment-compatibility gap, not a shortcut. The real C++ code content is exercised by loading the live route, not by this automated test. Nine tests cover: Space reveals (checked via the revealed face's `aria-hidden` state, not text presence — both flip faces are always mounted, so text-presence queries can't distinguish reveal state), reveal happens synchronously regardless of motion settings, Tip disappears on reveal, Explanation/rating controls appear only after reveal, keys 1-4 select the expected rating and only after reveal, a rating shortcut does not fire again once submitted, Space targeted at a focused control is not double-handled (see the honest caveat below), Space is prevented from scrolling, and held-key repeat does not duplicate the reveal.
One test's real strength is limited and said so in its own comment, not silently: the "focused control" test exercises the `isInteractiveTarget` guard's code path, but in this component the guarded action (`if (!revealed) setRevealed(true)`) is idempotent either way, so the scenario can't currently fail without the guard — it's a regression pin for future non-idempotent actions, not proof the guard is currently load-bearing.

**D24. Testing-library/react's auto-cleanup does not engage in this repo's Vitest config (no `globals: true`), which caused every render in the new test file to accumulate in the same document until an explicit `afterEach(cleanup)` was added.**
Not a design decision so much as a debugging note worth keeping: two tests failed with element-count mismatches (multiple "Good" buttons found, nine copies of answer text found) before this was diagnosed and fixed locally within the one new test file (not added to the shared `src/test/setup.ts`, to avoid any risk to the 13 other, DOM-free test files).

## 2026-07-23 — Phase E continued: Ordering, Matching, Walkthrough

All six v2 interaction types are now registered. Implemented per direct instruction; full detail in the PR report, decisions worth keeping here.

**D29. Ordering's keyboard path is explicit Move up/down buttons, not `@dnd-kit`'s `KeyboardSensor` — a deliberate deviation from what V1's ordering renderer does.**
V1 (`src/features/cards/renderers/ordering/Question.tsx`) does use `KeyboardSensor` with `sortableKeyboardCoordinates`, confirmed by inspection before building this. It was not reused for the v2 renderer for two reasons: (1) `KeyboardSensor` needs the row itself to be a keyboard-operable drag handle (Space to pick up, arrows to move, Space to drop), which means a non-button element intercepting Space — directly colliding with the Review shell's global Space handler (reveal/submit). Real `<button>` Move-up/down controls are excluded from that guard by construction (`isInteractiveTarget`), so there's no collision to reason about. (2) It composes cleanly with "drag-and-drop must not be the only interaction method" — the buttons are a complete, independent second path, not a fallback bolted onto the same mechanism. Mouse/touch drag still uses `@dnd-kit` (`PointerSensor` only, no `KeyboardSensor`), via a drag handle (`GripVertical`) that is `aria-hidden` and not in the tab order, since it does nothing keyboard-operable.
Boundary buttons (top item's "up", bottom item's "down") use `aria-disabled` + `pointer-events-none`, not the native `disabled` attribute — a browser force-blurs a focused element the moment it becomes natively disabled, which would eject focus the instant an item reaches an edge, defeating "keep focus on the moved item." Focus retention itself falls out of `key={id}` reconciliation on each row: moving an item re-renders the list, but React keeps the same DOM node (and therefore the same focused button) for a given id.

**D30. `ObjectiveResult` (`reviewPhase.ts`) gained an optional `score?: number` field for partial credit.**
Recall/Multiple Choice/Write Code stay binary and never set it. Matching (fraction of relationships correct) and Ordering/Walkthrough (fraction of positions/steps correct) do. `ReviewSessionScreen`'s `suggested` rating hint now reads it: fully correct suggests Good (3), partially correct (`score > 0`) suggests Hard (2) instead of flatly Again (1), still only ever a quiet hint the learner can override — the correctness/rating separation itself (spec) is unchanged.

**D31. Matching's v2 grading is uniform across fixed and unique (per-row) columns — no value-equality special case like V1's.**
V1's matching (`src/features/cards/renderers/matching/columns.ts`) has to branch: unique columns grade by pairing id, fixed columns grade by string value, because its fixed-column options are bare strings. V2's `MatchingColumn.items` always carry a stable `id`, fixed or not (a fixed column just shares one item list across every row) — so `gradeMatching` (`src/domain/grading/matching.ts`) is one code path: compare the chosen item id to the authored item id for that row+column, always. This is a byproduct of the schema already being more generalized (D13), not a new schema change.

**D32. The Review shell no longer coerces a `null` `autoGrade` result into `{correct: false}`.**
Exposed by Walkthrough: a walkthrough made entirely of `recall` steps (self-graded, like the top-level Recall interaction) has nothing objective to grade, so `aggregateWalkthroughResult` correctly returns `null` — but Walkthrough must be `interactive: true` (it needs a structured response, not a bare reveal), so it goes through `SUBMIT_RESPONSE`/`autoGrade`/`RESPONSE_VALIDATED`, and the shell's old fallback (`result ?? { correct: false }`) turned that legitimate `null` into "graded and wrong," which would have shown "Incorrect" and suggested Again for content nothing ever checked. `ReviewSessionScreen.primaryAction` now dispatches `autoGrade`'s result as-is; `null` reaches `reviewPhase`'s `feedback.result` unchanged (the phase type already allowed it), matching Recall's own self-graded convention. Multiple Choice/Write Code/Ordering/Matching are unaffected — their `autoGrade` never legitimately returns `null`.

**D33. Walkthrough's multi-step state lives entirely inside the shell's `response`/`setResponse` — the shell's phase machine only transitions once, at the very end.**
`WalkthroughState` (`interactions/walkthrough/state.ts`) tracks `stepIndex` plus per-step `answers`/`results`, all internal to the View. Every step is answered while the shell's phase stays `presenting`; only the last step's "Finish" button calls the shell's `onPrimaryAction`, which is what actually submits the card and reveals the Explanation/rating (spec: one Card, one final CardState/rating). "Each step records its first submitted objective result" is enforced by never overwriting an `answers`/`results` entry that already exists; step navigation (Previous, or revisiting via the progress dots) stays available even after the whole card is graded, purely for review, rendering already-answered steps read-only regardless.

**D34. Registered `orderingDefinition`/`matchingDefinition`/`walkthroughDefinition` in `interactions/registry.ts`; all six v2 interaction types now resolve.** The registry stays typed as `Partial<...>` (not a plain `Record`) so a future 7th interaction type still fails loudly via `getInteractionDefinition` instead of silently rendering nothing — same rationale as D28, just no longer describing a gap.

## 2026-07-23 — Phase D: CardState extraction (steps 1–3 of 6)

Per `itera-migration-plan.md` §4 and the shared `MigrationRunner` contract in §0. This milestone covers steps 1–3 (additive schema, backfill, dual-write) only — steps 4–6 (parity verification over a real observation period, read cutover, and later cleanup) are explicitly not started, matching the plan's own staging.

**D38. The new `CardState` row shape is `src/types/cardV2.ts`'s `CardState` interface exactly (including `suspended`), not the bare `SchedulingState` shape `itera-migration-plan.md` §4's prose literally describes.** `cardV2.ts`'s `CardState` was already the locked, documented target shape for this exact purpose ("so the eventual CardState split needs no translation layer" — its own doc comment). Inventing a second, slightly different intermediate shape now would only mean a translation step later, for no benefit. `suspended` — a top-level `CardBase` field in v1, not part of `SchedulingState` — is folded in here because that's `CardState`'s own design, not a new decision.

**D39. `CardState` is keyed by its own `cardId` field, not a synthetic `id`.** Dexie: `cardStates: 'cardId'` (inline primary key, version 3 — see `src/data/dexie/db.ts`). Supabase: a bespoke `createCardStateRepo` (`card_id text primary key references cards(id) on delete cascade`), since the generic `crud<T extends {id: ID}>` helper in `SupabaseRepository.ts` is hardwired to a field literally named `id` — the same reason `createCardRepo`/`createReviewRepo` are already bespoke in that file, not a new pattern.

**D40. Dual-write is wired into every call site that writes `Card.scheduling` or `Card.suspended`:** `useGradeCard` and `useUndoGrade` (v1 grading/undo), `usePersistReviewResult` (v2 grading, added this session), `useCreateCard` (initial `CardState` row for a new card), and `useSaveCard` (also the suspend-toggle path — dual-writes unconditionally on every save rather than trying to detect which fields changed, since rewriting `CardState` with unchanged values is harmless and idempotent). `useDeleteCard` also deletes the matching `CardState` row, to avoid an orphan — Postgres additionally enforces this via `on delete cascade`, but the app-level delete is what gives Dexie the same guarantee.

**D41. Reads are not cut over.** `getDue()` (both backends) and everywhere else that reads scheduling still reads `Card.scheduling` exclusively. `CardState` is write-only from the rest of the app's perspective right now — this is step 5 in the plan, deliberately not started here, since the plan requires a real parity-observation period (step 4) first and the product owner hasn't reviewed one.
